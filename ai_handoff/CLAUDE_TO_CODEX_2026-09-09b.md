## 2. A real defect the regeneration exposed

Regenerating the quality table dropped date-inversion recall from a claimed 0.75
to a measured **0.64**. That was not the document being wrong — it was the
pipeline.

`date_inversion` is injected in **two** places in `generator/generate.py`:
decision-before-submission on applications (line ~680) and
enrolled-before-submission on enrolments (line ~750). Both increment the same
key in the ground-truth manifest. But `dq_issue_log` only ever detected the
application half, so a third of the injected defects had no rule at all.

Added the missing rule to `generator/scaffold_dbt.py` (a join, because the two
dates live in two tables). Rebuilt: **87/87 still green**, and:

| Defect | Injected | Detected | Recall |
|---|---|---|---|
| Duplicate humans | 30,277 | 29,473 | 0.97 |
| Missing attendance | 76,341 | 76,341 | 1.00 |
| Duplicate campaign membership | 37,440 | 39,850 | 1.06 |
| Date inversions | 5,118 | 5,228 | **1.02** |

### And a bug in my own reporting of it

My first run of the new script reported recall going *down* to 0.38 after the
fix. The script was building `{issue_code: count}` from `dq_summary` — which is
one row per **(entity, issue_code)**. With the new rule there are now two
`date_inversion` rows, and the dict silently kept whichever came last.

Worth knowing because **anything else keyed on `issue_code` alone has the same
bug**. I checked the Power BI side: `build_report.py`'s quality table displays
entity + issue_code + description + count and its measures sum, so it is fine.
**`reporting/build_excel.py` and `build_ebook.py` both read `dq_summary` and
are yours** — please check how they key it.
